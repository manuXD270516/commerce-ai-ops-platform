## Context

Milestone M6. Arquitectura transversal en [architecture.md](../../../docs/architecture.md) §3 y §6 (decisión 9).

## Goals / Non-Goals

Objetivo: cumplir el gate de salida de M6: Macro-F1 y errores; reanudación durable; supervisor sin reglas de negocio. No objetivos: Especialistas completos (M7) y efectos privilegiados (M8).

## Decisions

1. **Comparación de proveedores bajo la restricción del proyecto.** config.yaml (autorización del 2026-09-29, reafirmada el 2026-10-01): sin claves de IA ni llamadas pagas; modelos locales o simulados etiquetados. Por eso OpenAI y Anthropic no se comparan en este milestone y no se registra ningún ID comercial. Candidatos comparados con el dataset versionado `router@0.1.0` (familias de plantillas, split por familia: 30 train / 23 dev / 23 holdout): `rules` (reglas explícitas), `classifier` (Naive Bayes multinomial local con unigramas y bigramas, entrenado sólo con train, artefacto `packages/ai/models/nb-model.v1.json` con sha256 del archivo de entrenamiento y control de drift en evals) y `rules+classifier` (reglas primero, clasificador sólo si ninguna regla aplica). En dev, `rules` y `rules+classifier` empatan (macro-F1 1.0) y `classifier` obtiene 0.65. Desempate fijado antes de mirar holdout: `rules+classifier`, porque la spec pide un clasificador acotado para lo que las reglas no cubren en lugar de rechazar todo lo no previsto. Holdout ejecutado una vez después de fijar la selección, sin ajuste posterior (resultado en verification.md). Síntesis de respuestas: `template-synth.v1`, determinístico y SIMULATED (decisión 6). Selección y versiones registradas en `SELECTED_PROVIDER` y en cada run (`router_version`, `model_version`, `prompt_version`).
2. **Router.** Orden fijo: contexto explícito de UI autenticado → reglas → clasificador con umbral 0.6 (debajo, aclaración `ambiguous`). Sólo devuelve intenciones permitidas (`order_investigation`, `product_recommendation`, `inventory_anomaly`, `out_of_scope`). Las intenciones múltiples se descomponen en el mismo run sin ampliar scopes. Una investigación de orden sin exactamente un `order_id` pide aclaración (`missing_order_id`, `multiple_order_ids`) y no consulta nada. Pedidos de precios, stock, reembolsos, datos de cuenta, aprobación o de ignorar instrucciones se rechazan con una limitación (`out_of_scope`). La extracción de slots sólo parsea texto (ids, montos con "menos de" estricto y "hasta" inclusivo, GB, SKUs); el supervisor no calcula precios, SLA, stock ni permisos.
3. **Grafo LangGraph JS.** `@langchain/langgraph` 1.4.18 y `@langchain/core` 1.2.13 (versiones de la decisión 9, verificadas al instalar). Nodos: `router` → `clarify` | `refuse` | `specialists` → `await_approval` (`interrupt`) → `execute_action` → `synthesize`. El valor de reanudación de la aprobación lo produce el executor leyendo la BD; ni el modelo ni el usuario pueden inyectarlo. El estado guarda datos, hallazgos, evidencia y decisiones; no hay razonamiento oculto.
4. **Checkpoints en PostgreSQL con RLS.** En lugar de `@langchain/langgraph-checkpoint-postgres` (tablas sin tenant ni RLS y DDL desde el runtime), `TenantCheckpointSaver` reutiliza la lógica de lectura de `MemorySaver` sobre un espejo hidratado desde `commerce.graph_checkpoints` / `graph_writes` (migración `0007_agent_graph.sql`, RLS por tenant, checkpoints sólo INSERT) y escribe cada checkpoint y pending write antes de devolver. Un proceso nuevo hidrata el mismo thread (= run) y reanuda.
5. **Ejecución durable, leases y recuperación.** El run (`agent_runs`: input, estado, outcome, uso, versiones, `cancel_requested_at`, lease) es el registro durable; el job de BullMQ `agent-runs` sólo notifica. `executeRun` toma un lease con `UPDATE … RETURNING` (otro worker sólo entra cuando expira), re-resuelve la membership del dueño del run en cada ejecución (revocada → `FAILED/ACCESS_REVOKED` sin efectos) y libera el lease al terminar. Un barrido cada 30 s (`agent-run-recovery`) reconstruye trabajo desde PostgreSQL: runs QUEUED cuyo job se perdió (p. ej. Redis reiniciado), RUNNING con lease vencido y WAITING_HUMAN con decisión. Sin Redis, la API ejecuta en proceso con el mismo executor (`RUN_EXECUTION=inline`).
6. **Presupuestos.** `Meter` controla 6 llamadas de modelo, 12 tools, 12.000 tokens y 60 s activos por run (overridable por run para pruebas), se verifica antes de cada llamada y se persiste en el estado del grafo y en el run; la espera humana no suma tiempo activo. El clasificador local cuenta como llamada de modelo; las reglas no. Agotado un presupuesto, el run termina `BUDGET_EXCEEDED` con la evidencia reunida y etiquetada como parcial, sin más llamadas. Los tokens de `template-synth.v1` son estimaciones (caracteres / 4) y se reportan como SIMULATED.
7. **Cancelación.** `POST /v1/agent-runs/:id/cancel` (dueño o support): QUEUED/WAITING_HUMAN se cancelan de inmediato y ningún worker los toma; un run en ejecución ve la cancelación antes de su próxima tool. Un efecto ya confirmado se informa, no se revierte.
8. **Tools desde el grafo.** `ToolGateway` es el único camino a tools: verifica cancelación y presupuesto y llama `invokeTool` (M5) con el contexto del dueño del run y el perfil del especialista (intersección de scopes). Cada llamada queda auditada con `correlation_id = run-<id>`. La recuperación de conocimiento autorizada cuenta como tool.
9. **API y SSE.** `POST /v1/agent-runs` → 202 + id; `GET /v1/agent-runs/:id`, `/evidence`, `/events` (SSE desde `run_events`, con `Last-Event-ID`/`?after=` para reenviar sólo lo perdido; reconectar nunca crea otro run) y `/cancel`. Customers sólo ven sus runs; support y approver los del tenant.

## Risks / Trade-offs

- El mismo autor escribió reglas y dataset; la separación de holdout es por familia de plantillas, no por autor ciego. Las cifras describen ese dataset sintético, no tráfico real.
- El fallback del clasificador falla en mensajes fuera de dominio que no cubren las reglas (ver verification.md); corregirlo es un `router.v2` con un nuevo holdout.
- El SSE consulta la BD cada 400 ms por conexión; suficiente para la demo, no para carga alta.
